FIRST THINGS FIRST

Should you even override?

The easiest way to avoid problems is not overriding equals at all.

chapter 3, item 10
When NOT to override

Four situations

EXCLUSIVE

Active entity

Thread: each instance is inherently unique, not a value.

NO LOGICAL EQUALITY

Not needed

Pattern: the architects decided nobody needs to compare by value.

ALREADY SOLVED

Superclass covers it

AbstractSet, AbstractList, AbstractMap.

And a fourth: a private or package-private class, where you are certain equals is never invoked.

The example that should not exist
UnwiseThread.java

Two distinct threads become "equal". Thread is an active entity, not a value.

When TO override

Value classes

When logical equality diverges from object identity - Integer, String, and today's examples.

Exception: classes with instance control (Item 1), such as enum, don't need it - logical equality already is identity.

Transitivity

x=y and y=z must imply x=z. The classic inheritance problem.

presented by Matheus Cruz
transitivity/Point.java

On its own, it obeys the contract. The trouble starts when a subclass adds a value component.

ColorPoint extends Point

Three attempts.

None of them solves symmetry, transitivity and Liskov at the same time.

Attempt A - compares only against its own type

Attempt B - ignores color in mixed comparisons

p1=p2 and p2=p3, but p1≠p3. And the second test: two siblings that delegate to each other overflow the stack.

A bonus consequence

Free StackOverflowError

Two different Point subclasses (ColorPoint and SmellPoint), each one "delegating to the other side" when the type doesn't match. A call to myColorPoint.equals(mySmellPoint) recurses forever.
Attempt C - getClass() instead of instanceof
ColorPointGetClass.java
ColorPointGetClassTest.java

Symmetric only among instances of the exact same type - but Point never changed its own equals, so p.equals(cp) is still true while cp.equals(p) is false. That remaining asymmetry against its own superclass is exactly what breaks Liskov.

The way out

Composition, not inheritance.

Recap

Reflexive, symmetric, transitive

  • Reflexivity: nearly impossible to break by accident
  • Symmetry: watch out when trying to bridge to another type
  • Transitivity: the classic problem is inheritance plus a value component

The fourth requirement

Immutable objects get it for free

If an object never changes, repeated calls to equals against the same argument always agree.

The JDK's real mistake

java.net.URL.equals() breaks this

It depends on resolving the hostname to an IP address - which requires network access and can change over time. The book itself calls it "a big mistake" that can no longer be fixed for compatibility reasons.
The same problem, without a real network dependency

Checkpoint

Consistency

  • Immutability solves consistency for free
  • equals should never depend on a volatile resource (network, clock, randomness)

OPTIMIZATION

Field order and derived fields

Compare what is cheap and likely to differ first.

performance/Polygon.java

area is a derived field, computed once in the constructor. Comparing two areas is far cheaper than comparing every vertex.

PolygonTest.java

A counter exposed by the test proves the short-circuit: 0 vertex comparisons when the areas already differ, 4 when they need to be checked.

Checkpoint

Performance

  • Cheap fields most likely to differ go first
  • Derived fields can save the expensive comparison
  • Never compare fields that are not part of the logical state
COMMON MISTAKES

Two classic ways to get it wrong

Forgetting hashCode, and overloading instead of overriding.

BrokenHashCode

equals overridden, hashCode is not. A HashSet fails to recognize "equal".

FixedHashCode

Same equals, with hashCode alongside it. The HashSet works.

HashCodeTest.java
Overload, not override
commonmistakes/OverloadNotOverride.java

equals(OverloadNotOverride), not equals(Object). Without @Override, the compiler never warns.

OverloadNotOverrideTest.java

Works when called directly. Inside a List, contains() uses equals(Object) - the overload is never called.

The defense

Always use @Override

With @Override, this exact code simply fails to compile - the error points straight at the problem, instead of becoming a silent bug discovered hours later.
MODERN ALTERNATIVES

Records and AutoValue

The same recipe, generated for you instead of hand-written.

records/PhoneNumberRecord.java

The same value as PhoneNumber, as a record. The compiler generates equals, hashCode and toString from the components.

PhoneNumberRecordTest.java

The same EqualsVerifier used on PhoneNumber also approves the record - same guarantee, zero lines of equals written.

Three paths to the same place

Manual, record, or AutoValue

MANUAL

This item's recipe

Full control, more code, more room for human error.

RECORD

Java 16+

Generated by the compiler, zero dependency, requires the type to be a plain aggregate of values.

AUTOVALUE

Google, pre-records

Generated via annotation processing - the historical predecessor to records.
