ANTES DE TUDO

Será que você deveria sobrescrever?

A forma mais fácil de evitar problemas é não sobrescrever equals.

capítulo 3, item 10
Quando NÃO sobrescrever

Quatro situações

EXCLUSIVA

Entidade ativa

Thread: cada instância é única por natureza, não um valor.

SEM IGUALDADE LÓGICA

Não há necessidade

Pattern: os arquitetos decidiram que ninguém precisa comparar por valor.

JÁ RESOLVIDO

Superclasse cobre

AbstractSet, AbstractList, AbstractMap.

É uma quarta: classe privada ou pacote-privado, onde você tem certeza de que equals nunca será chamado.

O exemplo que não deveria existir
UnwiseThread.java

Duas threads distintas ficam "iguais". Thread é uma entidade ativa, não um valor.

O teste que prova o problema
UnwiseThreadTest.java
Quando SOBRESCREVER

Classes de valor

Quando a igualdade lógica diverge da identidade do objeto - Integer, String, e os exemplos de hoje.

Exceção: classes com controle de instância (Item 1), como enum, não precisam - a igualdade lógica já é a identidade.

Transitividade

x=y e y=z devem implicar x=z. O problema clássico de herança.

apresentado por Matheus Cruz
transitivity/Point.java

Sozinho, obedece ao contrato. O problema começa quando uma subclasse adiciona um componente de valor.

ColorPoint extends Point

Três tentativas.

Nenhuma resolve simetria, transitividade e Liskov ao mesmo tempo.

Tentativa A - só compara com o próprio tipo
ColorPointBrokenSymmetry.java
ColorPointBrokenSymmetryTest.java

p.equals(cp) é true, cp.equals(p) é false. Simetria quebrada.

Tentativa B - ignora cor nas comparações mistas
ColorPointBrokenTransitivity.java
ColorPointBrokenTransitivityTest.java

p1=p2 e p2=p3, mas p1≠p3. E o segundo teste: dois irmãos que se delegam mutuamente estouram a pilha.

Consequência extra

StackOverflowError de graça

Duas subclasses diferentes de Point (ColorPoint e SmellPoint), cada uma "delegando para o outro lado" quando o tipo não bate. Uma chamada a myColorPoint.equals(mySmellPoint) recursa para sempre.
Tentativa C - getClass() em vez de instanceof
ColorPointGetClass.java
ColorPointGetClassTest.java

Simétrico só entre instâncias do mesmo tipo exato - mas Point não muda o próprio equals, então p.equals(cp) ainda é true e cp.equals(p) é false. É exatamente essa assimetria contra a própria superclasse que viola Liskov.

A saída

Composição, não herança.

ColorPoint não É um Point - ele TEM um Point.

ColorPointComposition.java
ColorPointCompositionTest.java
Recap

Reflexivo, simétrico, transitivo

  • Reflexividade: quase impossível violar por acidente
  • Simetria: cuidado ao tentar se interligar com outro tipo
  • Transitividade: o problema clássico é herança + componente de valor

O erro real do JDK

java.net.URL.equals() quebra isso

Depende da resolução do hostname para um endereço IP - o que exige acesso à rede e pode mudar ao longo do tempo. O próprio livro chama isso de "um grande erro" que não pode mais ser corrigido por compatibilidade.
O mesmo problema, sem depender de rede de verdade

Checkpoint

Consistência

  • Imutabilidade resolve consistência de graça
  • equals nunca deve depender de um recurso volátil (rede, relógio, aleatório)

OTIMIZAÇÃO

Ordem de campos e campos derivados

Comparar o que é barato e provável de divergir primeiro.

performance/Polygon.java

área é um campo derivado, calculado uma vez no construtor. Comparar duas áreas é muito mais barato que comparar todos os vértices.

PolygonTest.java

Um contador exposto pelo teste prova o short-circuit: 0 comparações de vértice quando as áreas já divergem, 4 quando precisam ser checados.

Checkpoint

Performance

  • Campos baratos e com maior chance de divergir vêm primeiro
  • Campos derivados podem poupar a comparação cara
  • Nunca compare campos que não fazem parte do estado lógico
ERROS COMUNS

Dois jeitos clássicos de errar

Esquecer o hashCode, e sobrecarregar em vez de sobrescrever.

BrokenHashCode

equals sobrescrito, hashCode não. HashSet não reconhece o "igual".

FixedHashCode

O mesmo equals, com hashCode ao lado. HashSet funciona.

HashCodeTest.java
Sobrecarga, não override
commonmistakes/OverloadNotOverride.java

equals(OverloadNotOverride), não equals(Object). Sem @Override, o compilador nunca avisa.

OverloadNotOverrideTest.java

Funciona quando chamado direto. Dentro de uma List, contains() usa equals(Object) - o overload nunca é chamado.

A defesa

Use @Override sempre

Com @Override, esse mesmo código simplesmente não compila - o erro aponta exatamente para o problema, em vez de virar um bug silencioso descoberto horas depois.
ALTERNATIVAS MODERNAS

Records e AutoValue

A mesma receita, gerada por você em vez de escrita à mão.

records/PhoneNumberRecord.java

O mesmo valor de PhoneNumber, como record. O compilador gera equals, hashCode e toString a partir dos componentes.

PhoneNumberRecordTest.java

O mesmo EqualsVerifier usado em PhoneNumber também aprova o record - mesma garantia, zero linhas de equals escritas.

Três caminhos para o mesmo lugar

Manual, record, ou AutoValue

MANUAL

A receita deste item

Controle total, mais código, mais chance de erro humano.

RECORD

Java 16+

Gerado pelo compilador, zero dependência, exige que o tipo seja um agregado de valores.

AUTOVALUE

Google, pré-records

Gerado por annotation processing - o antecessor histórico dos records.
